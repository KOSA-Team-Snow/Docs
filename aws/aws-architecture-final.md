# FlaskApp AWS 재해복구(DR) 설계도

> 이 문서는 v4 stack의 `record/` 기록과 `terraform/` 구조를 바탕으로, 처음 보는 사람도
> 읽을 수 있게 정리한 전체 AWS 설계 개요입니다.

## 0. 한 줄 요약

평소엔 **온프렘(회사 자체 서버실)** 에서 FlaskApp이 돌아갑니다. 온프렘이 죽었을 때를 대비해,
AWS에 **"불씨만 켜둔 예비 환경"** 을 미리 만들어 두는 것이 이 프로젝트입니다. 데이터는 평소에도
계속 AWS로 복사되고 있고, 비상시 스위치 하나(`dr_active=true`)만 켜면 앱 서버가 AWS에서 살아납니다.

---

## 1. 먼저 알아야 할 개념 2가지

**(1) DR = Disaster Recovery (재해복구)**
주 시스템(온프렘)이 고장 났을 때 대신 서비스를 이어받는 예비 시스템.

**(2) Pilot Light (파일럿 라이트 = 불씨 방식)**
가스레인지의 작은 불씨처럼, **비싼 부품(앱 서버)은 꺼두고, 데이터와 네트워크 같은 기반만 항상
켜두는** 방식입니다.

- 항상 켜둠 → 데이터베이스(RDS), 데이터 복제기(DMS), 네트워크, VPN
- 비상시에만 켬 → EKS(앱 서버), ALB(로드밸런서)

이렇게 하면 평소 비용은 적게 들고, 비상시엔 빠르게 살릴 수 있습니다.

---

## 2. 전체 그림 (단 하나의 큰 그림)

```text
   [온프렘 / 회사 서버실]                         [AWS 서울 리전 ap-northeast-2]
   172.16.0.0/16                                  VPC 10.20.0.0/16
 ┌──────────────────────┐                       ┌───────────────────────────────────┐
 │ 사용자→ HAProxy(VIP) │                       │  public subnet  : NAT, (ALB)      │
 │ → FlaskApp(평시 운영)│                       │  app subnet     : EKS 노드, (ALB) │
 │   → MariaDB(원본 DB) │═══ VPN 터널(IPsec) ═══│  data subnet    : RDS, DMS        │
 │                      │ 10.20 ↔ 172.16 양방향 │                                   │
 │ Bind9(내부 DNS)      │                       │  + S3(파일저장) + ECR(이미지창고) │
 └──────────────────────┘                       └───────────────────────────────────┘
        원본 DB 변경분 ────DMS가 계속 복사────▶ AWS RDS (예비 DB)
```

핵심만 보면:

- 두 세계(온프렘 / AWS)가 **VPN 터널**이라는 암호화된 전용 통로로 연결됩니다.
- 온프렘 DB의 변경 내용이 **DMS**라는 도구를 통해 AWS의 예비 DB로 끊임없이 복사됩니다.

## 3. 구성 요소 하나씩 (쉬운 설명 + 실제 값)

### 3-1. 네트워크 (VPC) — 모든 것이 들어가는 "땅"

VPC는 AWS 안에 만든 **나만의 사설 네트워크 구역**입니다. 주소 대역은 `10.20.0.0/16`.
이 땅을 용도별로 6개 구획(subnet)으로 나눴고, 안정성을 위해 두 개의 물리적 구역(AZ: 2a, 2c)에
나눠 배치했습니다.

| 구획 종류 | 주소 | 용도 | 인터넷 연결 |
|---|---|---|---|
| public(공개) | 10.20.0.0/24, 10.20.1.0/24 | NAT, ALB(로드밸런서) | 직접 연결(IGW) |
| app(앱) | 10.20.10.0/24, 10.20.11.0/24 | EKS 앱 서버 | NAT 통해 나감 |
| data(데이터) | 10.20.20.0/24, 10.20.21.0/24 | RDS, DMS | 외부 직접 불가 |

쉽게 비유하면:

- **public** = 정문 마당 (바깥과 직접 통함)
- **app** = 사무실 (밖에 나갈 땐 정문 경비실 NAT를 거침)
- **data** = 금고실 (외부 인터넷과 직접 안 통함, 가장 안전)

추가로:

- **IGW (Internet Gateway)**: VPC를 인터넷에 연결하는 정문.
- **NAT Gateway**: 안쪽 서버가 밖으로 나가서 업데이트는 받되, 밖에서 안으로는 못 들어오게 하는
  경비실. 평소 1개 운영(`nat_gateway_count=1`, 리허설 시 2개로 늘릴 수 있음).
- **S3 Gateway Endpoint**: AWS 내부 파일창고(S3)에 갈 때 인터넷을 안 거치고 내부 지름길로
  가게 해주는 통로. 추가 요금 없음.

### 3-2. VPN — 온프렘과 AWS를 잇는 암호화 통로

온프렘과 AWS를 **Site-to-Site VPN**(IPsec)으로 연결합니다. 양쪽이 마치 한 네트워크처럼 통신합니다.

| 부품 | 역할 |
|---|---|
| Customer Gateway | AWS가 바라보는 "온프렘 쪽 입구" 정보 (pfSense 공인 IP `125.131.208.229`) |
| Virtual Private Gateway (VGW) | AWS 쪽 VPN 입구 |
| VPN Connection | 둘 사이를 잇는 실제 터널 (안정성 위해 터널 2개 제공) |

- 라우팅 방식: 정적(Static). AWS는 `172.16.0.0/16`(온프렘)으로 가는 길을 VGW로 보냄.
- 실제 운영 기록상 **터널 2개 중 1개는 UP, 1개는 DOWN** 상태였는데, 최소 1개만 살아 있으면
  통신은 됩니다.

> **중요한 교훈(record/step-12):** 터널이 UP이어도 통신이 막힐 수 있습니다. AWS 라우팅은
> 멀쩡했지만, **온프렘 쪽 방화벽(pfSense, DB 서버의 UFW)** 이 AWS 대역 `10.20.0.0/16`을
> 차단하고 있어서 막혔습니다. 양쪽 방화벽 모두 상대 대역을 허용해야 통신이 됩니다.

### 3-3. RDS — AWS 쪽 예비 데이터베이스

온프렘 원본 DB(MariaDB)의 복사본을 담을 AWS 관리형 데이터베이스.

| 항목 | 값 |
|---|---|
| 엔진 | MariaDB 10.11 |
| 크기 | db.t4g.small (소형) |
| 구성 | Single-AZ(단일 구역, MVP라 이중화 안 함) |
| 저장소 | gp3 20GB |
| 공개 여부 | 비공개(외부 인터넷에서 직접 접근 불가) |
| 특이사항 | binlog 파라미터 설정 — DMS가 변경분을 따라잡으려면 필요 |

### 3-4. DMS — 데이터를 계속 복사해주는 "이삿짐 + 실시간 동기화" 도구

DMS(Database Migration Service)는 **온프렘 DB → AWS RDS** 로 데이터를 옮기고 계속 동기화합니다.

작동 방식 = **Full Load + CDC** 2단계:

1. **Full Load**: 기존 데이터를 통째로 한 번 복사.
2. **CDC (Change Data Capture)**: 그 이후 원본에서 바뀌는 내용(추가/수정/삭제)을 실시간으로
   따라 복사.

이렇게 해서 AWS의 예비 DB가 항상 원본과 거의 같은 최신 상태를 유지합니다.

> **기록상 교훈:**
> - 처음엔 시스템 테이블까지 다 복사하려다, **앱 데이터(`flaskapp` 스키마)만** 복사하도록
>   범위를 좁혔습니다(step-13).
> - DMS 연결 실패의 마지막 원인은 네트워크가 아니라 **DB 계정 권한**(`dms_user` Access denied)
>   이었습니다(step-12).
> - **주의: 온프렘이 살아있고 DMS가 도는 동안 AWS DB에 직접 쓰면 충돌(split-brain)** 이 납니다.
>   그래서 평소엔 DMS task를 자동 시작하지 않고(`dms_start_replication_task=false`) 수동으로만 켭니다.

### 3-5. S3 + ECR — 파일창고와 이미지창고 (둘 다 항상 켜둠)

- **S3 (proddata 버킷)**: 앱이 올리는 파일(이미지 등)을 저장. 버전관리·암호화(AES256)·외부공개차단이
  켜져 있음.
- **ECR**: FlaskApp의 도커 이미지를 보관하는 창고. EKS가 앱을 띄울 때 여기서 이미지를 가져감.
  태그 변경 불가(immutable) + 푸시 시 보안 스캔.

이 둘은 이미 존재하던 자원이라 Terraform이 새로 만들지 않고 **import(기존 것을 관리 대상으로
편입)** 해서 씁니다.

### 3-6. EKS + ALB — 비상시에만 켜지는 앱 서버 (불씨 부분)

여기가 Pilot Light의 핵심입니다. **평소엔 꺼져 있습니다.**

- **EKS**: 쿠버네티스(컨테이너 앱 실행 플랫폼). FlaskApp이 여기서 돕니다.
- **ALB (Application Load Balancer)**: 들어오는 웹 요청을 앱으로 분배하는 로드밸런서.
- **ALB Controller**: 쿠버네티스 설정에 맞춰 ALB를 자동으로 만들어주는 도우미(Helm으로 설치).

토글 동작 (`eks/cluster.tf`의 `count = var.dr_active ? 1 : 0`):

- `dr_active=false` (평시) → EKS, ALB 관련 자원이 **0개**. 즉 안 만들어짐.
- `dr_active=true` (비상) → EKS 클러스터 + 노드 + ALB Controller가 한 번에 생성됨.

> **실제 DR 테스트(step-14)에서 겪은 문제와 해결:**
> - 앱 Pod가 RDS에 연결 안 됨 → 노드에 엉뚱한 보안그룹이 붙어 있었음. Launch Template로
>   올바른 SG를 강제.
> - `id` 컬럼에 기본값 없음 에러 → DMS가 만든 테이블에 AUTO_INCREMENT가 빠져 있었음.
> 결론: ALB → FlaskApp → RDS/S3 경로가 정상 동작함을 확인.

### 3-7. 보안그룹(SG) — 각 자원의 "문지기"

보안그룹은 자원별로 "누가 어느 포트로 들어올 수 있나"를 정하는 방화벽입니다. 5종류:

| SG | 누구를 들여보냄 |
|---|---|
| ALB SG | 인터넷에서 오는 웹(80/443) |
| EKS Node SG | ALB에서 오는 트래픽 |
| Cluster SG | 노드 ↔ 컨트롤플레인 통신(443) |
| RDS SG | EKS 노드 / DMS 에서 오는 DB 접속(3306)만 |
| DMS SG | DMS가 나가는 통신 |

핵심 원칙: **DB(RDS)는 아무나 못 들어오고, 정해진 출처(앱 노드, DMS)만 허용**.

### 3-8. IAM — 권한 부여

- DMS가 VPC/CloudWatch를 쓸 수 있도록 하는 서비스 역할 2개(`dms-vpc-role`,
  `dms-cloudwatch-logs-role`).
- 이미 계정에 있으면 충돌하지 않게 `manage_dms_roles=false`로 끌 수 있음.

### 3-9. 관측(Observability) — 감시 장치 (항상 켜둠)

- **SNS**: 알림을 이메일로 보내는 통로.
- **CloudWatch 알람 2개**: ① DMS 복제 지연(CDC lag) ② RDS 저장공간 부족.
- **CloudWatch 대시보드**: DR 준비 상태를 한눈에 보는 화면.

## 4. 평시 vs 비상시 — 무엇이 켜지고 꺼지나

| 자원 | 평시 (`dr_active=false`) | 비상 (`dr_active=true`) |
|---|---|---|
| VPC / 서브넷 / VPN / NAT | 켜짐 | 켜짐 |
| S3 / ECR | 켜짐 | 켜짐 |
| RDS (예비 DB) | 켜짐 | 켜짐 |
| DMS (데이터 복제) | 켜짐 (task는 수동) | 켜짐 |
| 관측/알람 | 켜짐 | 켜짐 |
| **EKS (앱 서버)** | **꺼짐** | **켜짐** |
| **ALB (로드밸런서)** | **꺼짐** | **켜짐** |

비상 전환 핵심 명령: `terraform apply -var="dr_active=true"` → 앱 계층이 살아남.
복귀: `terraform apply -var="dr_active=false"` → 앱 계층만 삭제, 나머지는 유지
(기록 step-15: 16개 삭제, EKS/ALB만 사라짐).

## 5. 사용자 요청은 어떻게 흐르나 (비상 가동 시)

```text
사용자 → (DNS가 AWS ALB 주소를 가리키도록 전환) → ALB
       → EKS의 FlaskApp Pod → RDS(DB 읽기) / S3(파일 읽기쓰기)
```

DNS 전환(온프렘 Bind9의 도메인을 AWS ALB 주소로 바꾸기)은 **온프렘 담당자 몫**입니다.
이 stack은 ALB 주소만 뽑아서(`scripts/dr-step-16-aws-prepare.sh`) 전달합니다.

## 6. 대략적인 비용 감각 (서울 리전, 30일 기준)

| 상태 | 월 예상 고정비 | 비고 |
|---|---|---|
| 네트워크/VPN만 | 약 $89 | NAT + VPN이 대부분 |
| 평시 Pilot Light 전체 (EKS 제외) | 약 $175 | RDS + DMS + NAT + VPN + 관측 |
| 비상 가동 (EKS/ALB 추가) | 위 + EKS 제어판/노드/ALB 비용 | 켜둔 시간만큼만 |

핵심 포인트: **EKS를 평소에 꺼두는 것** 이 비용 절약의 핵심입니다. DMS와 VPN은 "켜져만
있어도" 시간당 과금됩니다.

## 7. 책임 경계 (이 stack이 하는 것 / 안 하는 것)

| 이 AWS stack이 담당 | 온프렘 담당자가 담당 |
|---|---|
| VPC, VPN(AWS쪽), RDS, DMS, EKS, ALB, S3, ECR, IAM, 관측 | Bind9 DNS 전환, pfSense IPsec 설정, HAProxy/Keepalived, 온프렘 MariaDB binlog/권한 |

즉 이 설계는 **AWS 절반**만 책임지며, 온프렘 쪽 설정이 맞아야 전체가 돌아갑니다.
