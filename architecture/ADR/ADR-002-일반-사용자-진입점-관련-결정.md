# ADR-002: MetalLB 대신 HAProxy + Keepalived 기반 진입 구조 선택

## 상태

승인됨

## 배경

ADR-001에서 정상 운영 시 외부 사용자 진입점은 On-premise에 두고, On-premise 장애 시 AWS DR 환경으로 전환하는 방향을 결정했다.

이에 따라 On-premise 내부에서 외부 사용자 트래픽을 Kubernetes 서비스 애플리케이션까지 전달하는 진입 구조를 결정해야 한다.

초기 설계도에는 `MetalLB Pool`이 명시되어 있었고, 동시에 `loadbalancer1`, `loadbalancer2` 두 개의 Load Balancer VM도 구성되어 있었다. 이로 인해 외부 진입 경로를 MetalLB가 담당하는지, 별도 Load Balancer VM이 담당하는지 역할이 명확하지 않았다.

현재 네트워크 대역은 다음과 같이 구분되어 있다.

| 구분 | VLAN | 역할 |
|---|---:|---|
| 사용자 진입망 | VLAN 10 | 외부 사용자가 서비스에 접근하는 대역 |
| Load Balancer VM 대역 | VLAN 20 | `loadbalancer1`, `loadbalancer2`가 위치한 대역 |
| Kubernetes 노드 대역 | VLAN 30 | Kubernetes control-plane/worker 노드가 위치한 대역 |
| 관리자 접근망 | VLAN 40 | 관리자가 인프라에 접근하는 대역 |

관리자 접근망인 VLAN 40에서 Kubernetes 노드 대역인 VLAN 30으로 접근하는 경로는 pfSense에서 허용 처리되어 있다.

설계 검토 과정에서는 다음 혼선이 있었다.

- 설계도에는 MetalLB Pool이 존재한다.
- 동시에 `loadbalancer1`, `loadbalancer2` VM도 존재한다.
- 처음에는 `loadbalancer1`, `loadbalancer2`가 관리자 접근 또는 사용자 진입 트래픽을 Kubernetes 클러스터로 넘겨주는 역할이라고 이해했다.
- 그런데 Load Balancer VM은 VLAN 20 대역에 위치해 있었다.
- Kubernetes 클러스터 노드는 VLAN 30 대역에 위치해 있다.
- 만약 Load Balancer VM이 HAProxy + Keepalived를 통해 Kubernetes Ingress로 트래픽을 전달하는 역할이라면, Load Balancer VM은 VLAN 30 대역에 직접 위치하거나 VLAN 30으로 명확히 라우팅 가능해야 한다.
- 반대로 MetalLB를 사용한다면 Kubernetes 내부에서 `LoadBalancer` 타입 Service에 외부 IP를 할당하므로, 별도 Load Balancer VM의 역할과 중복될 수 있다.

따라서 On-premise 진입 구조에서는 MetalLB와 별도 HAProxy 기반 Load Balancer 계층을 동시에 둘 것인지, 하나의 진입 방식으로 정리할 것인지 결정이 필요했다.

## 검토한 대안

### 대안 1: MetalLB 기반 Kubernetes LoadBalancer 사용

이 대안은 Kubernetes Ingress Controller Service를 `LoadBalancer` 타입으로 노출하고, MetalLB가 VLAN 10 대역의 IP Pool에서 External IP를 할당하는 방식이다.

```text
사용자
  ↓
MetalLB External IP
  ↓
NGINX Ingress Controller Service
  ↓
Application Service
  ↓
Application Pod
```

장점은 다음과 같다.

- Kubernetes 방식에 가깝고 Service `type: LoadBalancer`를 사용할 수 있다.
- Ingress Controller에 외부 IP를 직접 할당할 수 있다.
- 별도 HAProxy backend 설정을 줄일 수 있다.

하지만 다음 이유로 최종 채택하지 않았다.

- 이미 `loadbalancer1`, `loadbalancer2` VM이 존재하여 진입 계층 역할이 중복된다.
- MetalLB IP와 HAProxy VIP 중 DNS가 어느 쪽을 바라봐야 하는지 모호해진다.
- 장애조치 주체가 MetalLB인지 Keepalived인지 불명확해진다.
- VLAN 10 MetalLB Pool과 VLAN 20 Load Balancer VM의 관계가 복잡해진다.
- 운영자가 장애 발생 시 MetalLB, Ingress, HAProxy, pfSense 중 어느 계층부터 확인해야 하는지 흐려진다.

### 대안 2: HAProxy + Keepalived 기반 Load Balancer VM 사용

이 대안은 `loadbalancer1`, `loadbalancer2` 두 개의 VM에 HAProxy와 Keepalived를 구성하고, HAProxy VIP를 On-premise 사용자 진입점으로 사용하는 방식이다.

```text
사용자
  ↓
HAProxy VIP
  ↓
loadbalancer1 또는 loadbalancer2
  ↓
Kubernetes Worker Node의 Ingress NodePort
  ↓
NGINX Ingress Controller
  ↓
Application Service
  ↓
Application Pod
```

장점은 다음과 같다.

- 외부 진입 VIP를 Kubernetes 외부에서 명확히 관리할 수 있다.
- `loadbalancer1`, `loadbalancer2` 이중화 구성이 가능하다.
- Keepalived를 통해 VIP 장애조치를 수행할 수 있다.
- HAProxy가 Kubernetes Worker Node의 Ingress NodePort로 트래픽을 전달하므로 경로가 명확하다.
- pfSense와 VLAN 정책을 기준으로 트래픽 흐름을 통제하기 쉽다.

단점은 다음과 같다.

- HAProxy backend에 Kubernetes Worker Node IP와 NodePort를 관리해야 한다.
- Worker Node 추가/삭제 시 HAProxy backend 설정 변경이 필요할 수 있다.
- Ingress Controller Service의 NodePort를 고정해야 한다.
- Load Balancer VM에서 VLAN 30 Kubernetes 노드 대역으로 접근 가능한 라우팅과 방화벽 정책이 필요하다.

### 대안 3: MetalLB와 HAProxy + Keepalived 동시 사용

이 대안은 HAProxy VIP를 외부 진입점으로 두고, HAProxy가 다시 MetalLB가 할당한 Ingress External IP로 전달하는 방식이다.

```text
사용자
  ↓
HAProxy VIP
  ↓
HAProxy
  ↓
MetalLB External IP
  ↓
NGINX Ingress Controller
  ↓
Application Pod
```

이 구조는 기술적으로 가능하지만 최종 채택하지 않았다.

이유는 다음과 같다.

- 외부 진입 계층이 두 번 생긴다.
- HAProxy VIP와 MetalLB IP가 모두 필요해진다.
- 장애조치와 트래픽 추적 경로가 복잡해진다.
- 이번 프로젝트 규모에서는 중복 계층으로 인한 이점보다 운영 혼선이 크다.

## 결정 사항

MetalLB는 사용하지 않는다.

대신 `loadbalancer1`, `loadbalancer2` 두 개의 VM에 HAProxy와 Keepalived를 구성하여 On-premise 사용자 진입 지점을 제공한다.

Kubernetes Ingress Controller는 `LoadBalancer` 타입이 아니라 `NodePort` 타입으로 노출한다. HAProxy는 Kubernetes Worker Node의 Ingress NodePort로 트래픽을 전달한다.

최종 진입 경로는 다음과 같다.

```text
사용자
  ↓
HAProxy VIP
  ↓
loadbalancer1 또는 loadbalancer2
  ↓
Kubernetes Worker Node의 Ingress NodePort
  ↓
NGINX Ingress Controller
  ↓
Application Service
  ↓
Application Pod
```

구성요소별 책임은 다음과 같다.

| 구성요소 | 책임 |
|---|---|
| Keepalived | `loadbalancer1`, `loadbalancer2` 사이에서 VIP 장애조치 |
| HAProxy | 외부 트래픽을 Kubernetes Worker Node의 Ingress NodePort로 전달 |
| NGINX Ingress Controller | Host/path 기반 HTTP/HTTPS 라우팅 |
| Application Service | Ingress가 애플리케이션 Pod 집합으로 안정적으로 접근할 수 있는 내부 Service 제공 |
| Calico CNI | Kubernetes 내부 Pod/Service 네트워크 제공 |

최소 네트워크 정책은 다음과 같다.

| 출발지 | 목적지 | 포트 | 목적 |
|---|---|---:|---|
| 사용자망 VLAN 10 | HAProxy VIP | 80, 443 | 외부 서비스 접근 |
| Load Balancer VM | Kubernetes Worker Node VLAN 30 IP | Ingress NodePort 예: 30080, 30443 | HAProxy에서 Ingress로 전달 |
| 관리자망 VLAN 40 | Kubernetes Node VLAN 30 IP | 관리 포트 | 관리자 운영 접근 |
| Kubernetes Node | Pod/Service CIDR | CNI 정책에 따름 | 클러스터 내부 통신 |

목표 아키텍처는 다음과 같다.

```text
VLAN 10 사용자망
  |
  | 80/443
  v
HAProxy VIP
  |
  v
+-------------------+        +-------------------+
| loadbalancer1     |        | loadbalancer2     |
| HAProxy           |        | HAProxy           |
| Keepalived MASTER | <----> | Keepalived BACKUP |
+-------------------+        +-------------------+
  |
  | Ingress NodePort
  v
VLAN 30 Kubernetes Worker Nodes
  |
  v
NGINX Ingress Controller
  |
  v
Application Service
  |
  v
Application Pods
```

## 결정 근거

### 1. 외부 진입 책임을 한 곳으로 단순화

MetalLB와 HAProxy + Keepalived를 동시에 사용하면 외부 진입 IP를 누가 소유하고 관리하는지 모호해진다.

MetalLB는 Kubernetes `LoadBalancer` 타입 Service에 외부 IP를 할당하는 역할이고, HAProxy + Keepalived는 별도 VM 계층에서 VIP와 트래픽 분산을 담당한다.

현재 인프라에는 이미 `loadbalancer1`, `loadbalancer2` 두 개의 VM이 존재하므로, On-premise 외부 진입 책임은 해당 Load Balancer VM 계층으로 통일한다.

### 2. VLAN 경계와 운영 경로가 더 명확함

Kubernetes 노드는 VLAN 30 대역에 있고, 관리자는 VLAN 40 대역에서 접근한다. VLAN 40에서 VLAN 30으로의 접근은 pfSense에서 제어한다.

이 환경에서는 외부 진입 트래픽도 명확한 네트워크 경계를 통해 Kubernetes 노드의 Ingress NodePort로 전달하는 편이 운영상 이해하기 쉽다.

Load Balancer VM은 다음 조건을 만족해야 한다.

- 사용자 진입 VIP를 제공할 수 있어야 한다.
- Kubernetes 노드 대역인 VLAN 30의 Worker Node NodePort로 접근 가능해야 한다.
- VLAN 20에 위치한다면 pfSense 또는 L3 라우팅을 통해 VLAN 30으로 접근 가능해야 한다.
- 방화벽 정책상 Load Balancer VM에서 Kubernetes Worker Node의 Ingress NodePort로 가는 트래픽이 허용되어야 한다.

### 3. MetalLB IP 풀과 로드 밸런서 VM의 역할 중복 제거

MetalLB를 사용하면 Kubernetes Service가 직접 외부 IP를 할당받는다.

반면 HAProxy + Keepalived를 사용하면 외부 사용자는 HAProxy VIP로 접근하고, HAProxy가 Kubernetes Worker Node의 NodePort로 트래픽을 넘긴다.

두 구조를 동시에 사용하면 다음 혼선이 생긴다.

- DNS가 MetalLB IP를 바라봐야 하는지 HAProxy VIP를 바라봐야 하는지 불명확하다.
- 장애조치 주체가 MetalLB인지 Keepalived인지 불명확하다.
- 외부 진입 정책을 Kubernetes 내부에서 관리할지, 별도 LB VM 계층에서 관리할지 불명확하다.
- 운영자가 장애 발생 시 어느 계층부터 확인해야 하는지 복잡해진다.

따라서 이번 프로젝트에서는 MetalLB Pool을 제외하고, HAProxy VIP를 단일 On-premise 외부 진입점으로 사용한다.

### 4. 트러블슈팅 경로가 명확함

HAProxy + Keepalived 구조에서는 장애 발생 시 다음 순서로 트래픽을 추적할 수 있다.

```text
HAProxy VIP
  ↓
HAProxy 상태
  ↓
VLAN 20 -> VLAN 30 라우팅
  ↓
Worker Node Ingress NodePort
  ↓
NGINX Ingress Controller
  ↓
Application Service
  ↓
Application Pod
```

특히 `loadbalancer1`, `loadbalancer2`가 VLAN 20 대역에 위치해 있으므로, 이 VM들이 Kubernetes 노드가 있는 VLAN 30으로 트래픽을 전달할 수 있는지 확인해야 한다.

확인 항목은 다음과 같다.

- Load Balancer VM에서 Worker Node VLAN 30 IP로 라우팅 가능한가?
- Load Balancer VM에서 Ingress NodePort 포트로 접근 가능한가?
- pfSense 방화벽 정책에서 VLAN 20 -> VLAN 30 접근이 허용되어 있는가?
- 응답 트래픽의 return route가 정상인가?
- HAProxy backend가 Worker Node의 VLAN 30 IP와 고정 NodePort를 바라보고 있는가?
- DNS는 MetalLB IP가 아니라 HAProxy VIP를 바라보고 있는가?

## 영향

### 긍정적 영향

- 외부 진입점이 HAProxy VIP 하나로 명확해진다.
- MetalLB Pool 관리가 필요 없어져 설계가 단순해진다.
- Load Balancer VM 2대를 활용한 고가용성 구성이 가능하다.
- Kubernetes 외부 네트워크 정책과 Kubernetes 내부 라우팅 책임이 분리된다.
- 운영자는 HAProxy, Keepalived, pfSense, NodePort 기준으로 트래픽 흐름을 추적할 수 있다.

### 부정적 영향

- HAProxy backend에 Kubernetes Worker Node IP와 NodePort를 관리해야 한다.
- Worker Node 추가/삭제 시 HAProxy backend 설정 변경이 필요할 수 있다.
- Ingress Controller Service의 NodePort를 고정해야 한다.
- Load Balancer VM에서 VLAN 30 Kubernetes 노드 대역으로 접근 가능한 라우팅과 방화벽 정책이 반드시 필요하다.
- MetalLB를 사용했을 때처럼 Kubernetes Service가 외부 IP를 자동으로 할당받지는 않는다.

## 결정 사항 요약

이번 프로젝트에서는 MetalLB를 사용하지 않고, `loadbalancer1`, `loadbalancer2` 두 개의 VM에 HAProxy + Keepalived를 구성한다.

MetalLB Pool은 설계에서 제외하며, On-premise 외부 사용자 진입은 HAProxy VIP로 단일화한다.

Kubernetes Ingress Controller는 `LoadBalancer` 타입이 아니라 `NodePort` 타입으로 노출하고, HAProxy는 Kubernetes Worker Node의 Ingress NodePort로 트래픽을 전달한다.

최종적으로 이 결정은 외부 진입 책임 중복을 제거하고, VLAN/pfSense 기반 On-premise 네트워크 운영 모델에 맞게 트래픽 흐름을 명확히 하기 위한 것이다.
