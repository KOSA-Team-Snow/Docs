# ADR-001: 하이브리드 DR 아키텍처의 외부 사용자 진입점 결정

## 상태

승인됨

## 배경

프로젝트는 On-premise Kubernetes를 기본 운영 환경으로 사용하고, On-premise 장애 발생 시 AWS에서 서비스를 복구하는 Hybrid DR 아키텍처를 목표로 한다.

설계 초기에는 AWS를 유일한 외부 사용자 진입점으로 두는 구조를 검토했다.

```text
사용자
  ↓
AWS Route 53
  ↓
AWS ALB
  ↓
AWS EC2 HAProxy
  ↓
Site-to-Site VPN
  ↓
On-premise Kubernetes
```

이 구조에서는 On-premise를 인터넷에 직접 공개하지 않고, AWS를 Front Door로 사용한다. 정상 운영 시에도 사용자는 AWS ALB로 접근하고, AWS의 EC2 HAProxy가 VPN을 통해 On-premise Kubernetes로 트래픽을 전달한다.

초기에는 이 구조를 기반으로 다음 확장 방향까지 고려했다.

- On-premise를 Primary 운영 환경으로 유지한다.
- AWS는 외부 사용자 진입점 역할을 한다.
- 트래픽이 증가하면 일부 트래픽을 AWS EKS로 넘겨 Cloud Bursting을 수행한다.
- On-premise 장애 시에는 AWS EKS에서 DR 서비스를 운영한다.

하지만 검토 과정에서 AWS를 항상 외부 진입점으로 사용하면서 Cloud Bursting까지 포함하면, AWS가 단순 DR 환경이 아니라 정상 운영 트래픽에도 관여하는 Active 확장 환경이 된다고 판단했다.

이 경우 설계의 중심이 `Disaster Recovery`인지, `Hybrid Active 운영 + Cloud Bursting`인지 모호해진다.

따라서 최종적으로는 외부 진입점을 정상 운영과 DR 운영에서 분리하는 방향으로 설계를 변경했다.

## 검토한 대안

### 대안 1: AWS를 유일한 외부 사용자 진입점으로 사용

이 대안은 정상 운영과 DR 운영 모두에서 사용자가 AWS로 먼저 접근하는 구조이다.

```text
사용자
  ↓
AWS Route 53
  ↓
AWS ALB
  ↓
AWS EC2 HAProxy
  ↓
VPN
  ↓
On-premise Kubernetes
```

장점은 다음과 같다.

- On-premise를 인터넷에 직접 노출하지 않을 수 있다.
- 외부 공개 지점이 AWS ALB로 단순화된다.
- AWS WAF, ACM, Security Group, CloudWatch 같은 관리형 기능을 외부 진입 계층에 적용할 수 있다.
- DR 전환 시 사용자 도메인은 그대로 유지된다.

하지만 다음 이유로 최종 채택하지 않았다.

- AWS가 정상 운영 트래픽 경로에 항상 포함된다.
- On-premise가 정상이어도 AWS ALB, EC2 HAProxy, VPN 장애가 있으면 서비스 접근에 영향이 생긴다.
- Cloud Bursting까지 포함하면 AWS가 DR 대기 환경이 아니라 정상 운영 확장 환경이 된다.
- DR 설계의 목적이 `장애 시 복구`인지 `상시 하이브리드 운영`인지 흐려진다.
- 프로젝트 발표와 구현 범위에서 DR 시나리오의 메시지가 약해질 수 있다.

### 대안 2: AWS Front Door + Cloud Bursting 포함

이 대안은 AWS를 외부 진입점으로 두고, On-premise를 Primary로 운영하되 트래픽 증가 시 AWS EKS로 일부 트래픽을 분산하는 구조이다.

```text
사용자
  ↓
AWS ALB
  ↓
트래픽 일부는 On-premise
트래픽 일부는 AWS EKS
```

이 구조는 확장성 측면에서는 매력적이다. 하지만 Cloud Bursting을 제대로 설계하려면 다음 문제가 추가된다.

- On-premise와 AWS EKS 간 세션 처리
- 동일 애플리케이션의 양쪽 동시 운영
- DB 쓰기 경로와 데이터 정합성
- 이미지/파일 저장소 일관성
- 트래픽 분산 기준
- 장애 상황과 단순 트래픽 증가 상황의 구분
- RDS Replica 승격 전 AWS EKS가 쓰기를 수행할 수 있는지 여부

이 문제들은 DR보다 Active-Active 또는 Hybrid Scaling에 가까운 주제이다.

따라서 이번 프로젝트에서는 Cloud Bursting 개념을 제외하고, DR에 집중한다.

### 대안 3: 정상 운영은 On-premise 진입, 장애 시 AWS DR 진입

이 대안은 최종 채택한 구조이다.

정상 운영에서는 On-premise가 사용자 요청을 직접 받는다.

```text
사용자
  ↓
On-premise 진입점
  ↓
Kubernetes Ingress
  ↓
FlaskApp
  ↓
On-premise MariaDB
```

장애 발생 시에는 AWS DR 환경으로 진입점을 전환한다.

```text
사용자
  ↓
AWS ALB
  ↓
EKS Ingress
  ↓
FlaskApp on EKS
  ↓
AWS RDS MySQL
```

이 구조는 정상 운영과 DR 운영의 책임을 명확히 분리한다.

- 정상 운영 책임: On-premise
- 장애 복구 책임: AWS
- 전환 기준: On-premise 장애 및 운영자의 DR 선언
- 전환 방식: Route 53 레코드를 On-premise 진입점에서 AWS ALB로 변경

## 결정 사항

AWS를 정상 운영의 유일한 외부 사용자 진입점으로 사용하지 않는다.

정상 운영 시 외부 사용자 진입점은 On-premise에 둔다. On-premise 장애가 발생하고 운영자가 DR 전환을 선언한 경우에만 AWS 진입점으로 전환한다.

최종 방향은 다음과 같다.

```text
정상 운영 = On-premise Primary
DR 운영 = AWS Recovery
Cloud Bursting = 이번 범위에서 제외
```

정상 운영:

```text
사용자
  ↓
Route 53
  ↓
On-premise 진입점
  ↓
pfSense / Load Balancer
  ↓
Kubernetes Ingress
  ↓
FlaskApp Pod
  ↓
On-premise MariaDB Primary
```

DR 운영:

```text
사용자
  ↓
Route 53
  ↓
AWS ALB
  ↓
EKS Ingress
  ↓
FlaskApp Pod on EKS
  ↓
AWS RDS MySQL Primary
```

데이터 흐름:

```text
On-premise MariaDB Primary
  ↓
AWS DMS CDC
  ↓
AWS RDS MySQL Replica

FlaskApp image
  ↓
AWS ECR

Image upload file
  ↓
AWS S3 bucket
```

AWS는 평상시에 DR에 필요한 핵심 리소스만 준비하고, On-premise 장애 시 Route 53을 AWS ALB로 전환하여 DR 환경에서 서비스를 운영한다.

## 결정 근거

### 1. DR이라는 주제를 명확히 유지

이번 프로젝트의 핵심은 Hybrid Cloud 운영 자체가 아니라 On-premise 장애 발생 시 AWS에서 서비스를 복구하는 DR 구조이다.

AWS를 정상 운영의 상시 진입점으로 두고 Cloud Bursting까지 포함하면, 설계는 DR보다 Hybrid Active 운영에 가까워진다.

따라서 정상 운영은 On-premise에 두고, AWS는 장애 시 서비스를 이어받는 DR 환경으로 분리한다.

### 2. 정상 운영과 장애 운영의 역할 분리

최종 구조에서는 정상 운영과 DR 운영의 책임이 명확하다.

| 상태 | 사용자 진입점 | 애플리케이션 실행 위치 | DB |
|---|---|---|---|
| 정상 운영 | On-premise 진입점 | On-premise Kubernetes | On-premise MariaDB Primary |
| DR 운영 | AWS ALB | AWS EKS | AWS RDS MySQL Primary |

이렇게 분리하면 장애 전환 시 어떤 환경이 Active인지 설명하기 쉽다.

### 3. Cloud Bursting으로 인한 복잡도 제외

Cloud Bursting은 단순히 트래픽을 AWS로 보내는 문제가 아니다.

AWS EKS가 정상 운영 중 일부 트래픽을 받으려면 DB 쓰기, 세션, 파일 저장소, 네트워크 지연, 배포 동기화, 장애 시점의 데이터 정합성까지 함께 해결해야 한다.

이번 프로젝트에서는 AWS S3를 단일 이미지 저장소로 사용하고, On-premise MariaDB 변경분을 AWS DMS CDC로 RDS에 복제하는 DR 구조에 집중한다. AWS EKS는 평상시 트래픽을 받지 않고, 장애 시 생성 또는 활성화되는 복구 환경으로 둔다.

### 4. 장애 전환 시나리오가 단순해짐

최종 구조의 장애 전환 흐름은 다음과 같다.

```text
1. On-premise 장애 감지
2. 운영자가 DR 전환 선언
3. DMS replication lag 확인
4. AWS RDS Replica를 Primary로 승격
5. Terraform으로 EKS 및 node group 생성
6. ECR 이미지로 FlaskApp 배포
7. EKS Ingress ALB 생성 확인
8. Route 53을 On-premise 진입점에서 AWS ALB로 전환
9. 서비스 검증
```

이 흐름은 “정상 운영은 On-premise, 장애 시 AWS”라는 메시지를 명확하게 보여준다.

### 5. 비용과 구현 범위 관리

EKS와 node group을 상시 운영하지 않고 장애 시 생성하는 Pilot Light DR 방식을 유지할 수 있다.

상시 운영 리소스는 DR에 필요한 최소 요소로 제한한다.

- Route 53
- S3 bucket
- ECR repository
- RDS MySQL Replica
- AWS DMS CDC task
- Terraform state backend
- VPN 또는 AWS-On-prem 연결 경로

반면 AWS EKS 실행 환경은 장애 시점에 Terraform으로 생성한다.

이 방식은 Warm Standby나 Active-Active보다 비용과 구현 범위를 줄일 수 있다.

## 영향

### 긍정적 영향

- DR이라는 프로젝트 주제가 명확해진다.
- 정상 운영과 장애 운영의 책임이 분리된다.
- Cloud Bursting으로 인한 Active-Active성 복잡도를 제외할 수 있다.
- On-premise 장애 시 AWS로 전환하는 시나리오를 발표와 데모에서 설명하기 쉽다.
- EKS를 상시 운영하지 않아 비용을 줄일 수 있다.
- RDS Replica, S3, ECR, DMS 중심의 Pilot Light DR 구조가 명확해진다.

### 부정적 영향

- 정상 운영 중 On-premise 진입점은 외부 사용자 트래픽을 직접 받을 수 있어야 한다.
- On-premise 공개 구간에 대한 pfSense, 방화벽, VLAN, Load Balancer 보안 정책이 중요해진다.
- AWS ALB를 상시 Front Door로 두는 구조보다 On-premise 외부 노출 관리가 더 필요하다.
- Cloud Bursting은 이번 설계 범위에서 제외되므로 트래픽 증가 대응은 On-premise 확장 또는 별도 후속 설계가 필요하다.
- DR 전환 시 Route 53 전환, RDS 승격, EKS 생성 시간이 RTO에 포함된다.

## 결정 사항 요약

초기에는 AWS를 유일한 외부 사용자 진입점으로 두고, On-premise를 Primary로 운영하면서 트래픽 증가 시 AWS로 Cloud Bursting하는 구조까지 검토했다.

하지만 Cloud Bursting을 포함하면 설계가 DR이 아니라 Hybrid Active 운영에 가까워지고, 프로젝트의 핵심 메시지가 흐려진다.

따라서 최종적으로는 정상 운영 진입점은 On-premise에 두고, On-premise 장애 시 AWS ALB와 EKS 기반 DR 환경으로 전환하는 구조를 선택한다.

```text
최종 결정:

정상 운영은 On-premise에서 수행한다.
AWS는 정상 운영 트래픽의 상시 진입점이 아니다.
AWS는 DR 전환 시 사용자 진입점과 애플리케이션 실행 환경을 제공한다.
Cloud Bursting은 이번 프로젝트 범위에서 제외한다.
```
